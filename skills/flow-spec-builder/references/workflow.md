# 对话与执行流程

顺序与等待点以 [用户流程与确认节点](user-journey.md) 为准。本文件描述八步的实际做法，交付细节见 [完整交付契约](delivery-contract.md)。

## 1. 接收参考资料

图片必须有顺序；发布标题、正文、标签可选。已有顺序与资料直接使用。文案缺失且意愿未知时，按user-journey明确询问是否现在补充或先做图片、稍后再补；已有答案沿用。图片顺序只确认歧义；不问用途、账号定位、账号资料。保存到工作目录 reference/，保持扩展名和原始内容，不伪造缺失文案。

## 2. 分析参考图文

按 image-prompt-guide.md 逐张记录并横向比较：页型、固定视觉规则、变化内容、分页编号、角色、文字到画面的关系。有发布文案时也分析标题结构、正文组织、标签及与图片的关系；只有图片时明确分析范围。

同套不同页型分开抽象；共享规则不能把正文胶囊标题等样式强加到封面尾页。单样本规则标注不确定，不把参考套图的具体页数、人物或题材提升为全局规律。给用户简短发现和一个例子，按ui-output-contract生成独立的02-analysis阶段HTML；这一步不强制创建完整flow/spec三件套。

## 3. 原内容回填还原与对照

### 3.0 全套覆盖，不默认抽样

按用户提供的原顺序准备所有参考页的还原方案，一张对应一张，提供逐页覆盖表。模板可以按页型共用，但测试页不能因此减少。仅用户明确选定抽样或部分范围后才缩减，并列明未覆盖页。不要自行把“先测代表性版式”作为默认首轮。

特殊页、缺失素材、不可辨文字需单独说明并提出处理方案，不静默遗漏；执行器单批上限通过分批处理。实际生成仍在完整方案展示并确认之后，已有授权不重复询问。

### 3.1 先做模板，再填原文

- 先按 design 四层写可复用模板：风格、图文关系、变化槽位、不照搬。原主题词、句子、物件、人物具体外形放入输入值。
- 依原顺序转写文字，保留原意、编号及页型对应；看不清的关键字先确认。原笔记发布标题不能与封面标题混为一项。
- 整理 sample_input，仅表示本轮还原内容。需要还原角色时提取为 hero 文字值，不索要角色图，不默认决定长期角色。
- 固定构图可以写具体布局尺度；由内容变化的动作、物件不得写死。若必须保存逐图描述才能还原，标记为临摹基线，不能当成可复用模板的验证。
- 实际提示词允许具体化，但应从同一页型模板与槽位推导。不能为每张测试图暗改模板、不记录额外人工指令。

写初版 flow.json，运行 validate、plan；需要基础文字规格时再render。按ui-output-contract生成03-plan的独立HTML，已交付阶段不覆盖。对用户展示三层对应：**模板全文（含槽位）→原内容填充值→每次实际完整提示词**，以及页型、张数、调用数、尺寸、比例差异、图片输入0。原文逐字呈现要求写入提示词。

### 3.2 执行与验收

具体方案确认后按 execution-validation.md 生成，原图不传入生图工具，前一张生成图也不传。保存真实调用和原始结果；新方案默认先确认，已确认同一方案不用反复问。

另存03-result阶段HTML，与03-plan相互链接；用户验收后新增结果版本并保留此前待验收版本。并排对照原图，检查风格、布局、分页、编号、文字与画面意义、额外文字。用户认可则记录范围和已知偏差，冻结视觉模板；未认可时只改有证据的1—2处，另立版本，不无限重抽。第4步在验收后进行；用户明确跳过或仅做分析时标记未实测并继续其授权范围。

## 4. 确认这一套流程的复用方式

提供有依据的建议，集中确认：
- 以后输入主题/标题、完整文案，还是其他必要内容；哪些由文字模型写，哪些逐字保留。
- 图片数量固定、按内容自动分页，或用户指定；合理上下限、每页容量、溢出怎么处理；封面和尾页是否计入。
- 是否产出发布标题、正文、标签；缺原文时新增写作逻辑只能标为新设计，不能说已复刻其规律。
- 哪些是固定预设，哪些是可替换槽位；生成文字后是否先让用户看。

这些选择仅针对当前参考导出的流程，不能视为所有主题的统一设置，也不能从还原样例推定。角色存在时再问：是否固定、套内一致还是每张可变。想长期固定也可采用文字设定；只有用户选择图像保真才收角色资产。无角色则不问。

现有字段映射：变化文字→inputs；固定风格/关系→prompt与design；按两条一页→grouped(2)与multiple_of；原文保留→verbatim；停顿→confirm。纯文字角色使用 hero 槽位，不填 subject.fixed；图片固定角色才用 subject、presets 和保留清单。用户以后要换的外形、口头禅、道具不能写死。inputs.default 只供预填，不参与运行。

## 5. 编写完整复刻流程

按 spec-definition.md 和 flow-json.md 写源文件。从示例借结构，不复制其特定主题或图片依赖。

保留已认可的视觉模板；需要主题扩写、内容规划、发布文案时新增文字步骤及完整输出格式；编号、分组、填槽位等确定规则交给脚本。说明每一步输入来源、输出去向、调用次数及实现状态。不能把 Agent 手工写的测试文案冒充已跑过的文字生成步骤。

模型绑定与执行能力如实披露：具体已配置型号、待绑定，或内置工具未披露型号。不能用 flow.models.image 推断实际内置模型。仅纯文字输入的文字步骤不强制具备看图能力。

离线检查：
```bash
python3 <技能目录>/scripts/flowkit.py validate <玩法目录>/flow.json
python3 <技能目录>/scripts/flowkit.py render <玩法目录>/flow.json
python3 <技能目录>/scripts/flowkit.py plan <玩法目录>/flow.json
```

validate 错误自行修正；D13～D17 是提醒，缺发布文案、迁移输入按当前范围记录，不编造数据消除提醒。现有执行器不能表达的系统消息、运行时附加格式或脚本操作，在 handoff 中明确待实现，不能写不存在的字段后声称能直接运行。

## 6. 展示完整流程说明

主动交付完整流程HTML主入口，抽屉内可查看所有步骤全文；flow.json与spec.md在“源文件/交接文件”次级入口提供，用户不必同时审阅三份。按 delivery-contract.md 整理，不能只给简化预览或把完整模板藏在日志。

用户先看全局：输入什么→文字模型做什么→脚本如何拆页填槽位→图片模型每次画什么→得到多少图片和发布文案。再看每步全文、模型、槽位、数据格式、次数公式、异常处理和测试覆盖。系统消息不存在就写无；未绑定模型就写待绑定，不虚构。

新增完整流程需要确认时停下展示具体方案；同时说明还原验证过哪些部分，是否建议补充测试。不要让用户审核代码才能做决定。

## 7. 按需补充测试

按用户选择检查新主题输入链路、文字规划步骤或迁移。先准备具体新输入、展开提示词、页数、调用数及测试目的，保存07-plan独立HTML，展示后按已有授权执行；结果另存07-result，保持前后可回看。

迁移冻结已认可模板，仅换约定内容字段，默认保持 hero；若改模板/人物，则标新版本或新测试变量。新增文字步骤需保存真实输出；文字模型未绑定时，可测试生图部分，但不能宣称端到端通过。只做还原时说明迁移未验证，不强制补跑才能交付。

## 8. 定稿交付

按case-operations.md用casebook deliver生成三个核心文件flow.html、flow.json、spec.md；reference/必需，presets/按需，tests/只保存真实执行证据。按清单打包，核验文件数与链接，更新固定入口。第8步不应等用户额外追问才补上；前面已认可且资料齐全就完成已授权交付。未实测或明确跳过的部分如实标注。基础脚本之外的实现需求写清楚交给后续工具，不自动创建网站或应用。

## 执行器与命令

内置工具由 Agent 编排，使用当前工具说明；没有配置外部接口不阻塞可用的内置生图。flowkit 的 run 只用于外部 API，不能调用内置生图。

| 命令 | 作用 |
| --- | --- |
| validate FLOW | 离线检查规格 |
| render FLOW [-o spec.md] | 生成基础流程规格；完整交付另按契约补充 |
| plan FLOW [--transfer] | 展开还原/迁移预览；含未执行文字步骤时可能仍有待定值 |
| plan --run-dir D | 从真实运行状态展开提示词 |
| run FLOW [--input F 或 --transfer] [--stop-before-images] | 使用已配置外部API真实运行 |
| run --resume D [--redo STEP] | 继续或重跑 |
| init-env / check-api | 仅外部API路径需要；check-api --image 会实际生图 |

外部API配置使用 Base URL、API Key、实际可用模型；密钥不写进交付文档。先跑文字再停图可用 --stop-before-images，检查真实输出后继续。不要把安装、plan、HTML预览成功当成生成成功。
