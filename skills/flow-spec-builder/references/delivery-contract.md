# 完整流程交付契约

## 最终交付的三个核心文件（不是每一步都要产出）

| 文件 | 用途 |
| --- | --- |
| flow.html | 用户主入口：全局流程及可展开的每步全文，可离线阅读和复制提示词 |
| flow.json | 模板、输入、步骤、连接与交付补充的结构化源 |
| spec.md | 可直接交给其他工具的完整文字规格，内容与HTML一致 |

过程默认只展示当前阶段HTML；阶段文件按 [分阶段页面契约](ui-output-contract.md) 保存。第2步不必生成完整flow.json和spec.md。用户主要审阅HTML，其他两种格式服务机器读取和后续交接，内容从同一源派生。

reference/ 保存有顺序的原图，原笔记标题/正文/标签原样存于 reference 字段；缺失就记录。presets/ 仅在用户选定模式需要时提供。tests/ 仅保存实际测试：输入、实际提示词、原始输出、对照页、执行记录和用户验收。总文件数随原图、测试次数变化；交付时清点实际文件并区分3个主文件和附件，不承诺只有3个文件。

## 用户必须看得见的全局信息

1. 参考来源、页型与规律；哪些来自观察，哪些是新增设计。
2. 以后使用这套流程要输入什么、固定什么、可改什么；示例输入与输入契约分开。
3. 全局步骤与连接、分页和数量公式、一次正常运行的文字/图片调用数与最终图片数。重试、修复和修图另记，不能混入正常调用数。
4. 具体文字/图片模型及执行器；未选就写待绑定，内置工具未披露就写未披露。脚本配置型号与实际调用分开；不照搬示例里的型号。
5. 完整可复制的提示词、槽位表、运行时拼接和输出格式；不能省略系统消息、JSON约束或隐藏后缀。有则写全文，无则明确写无。
6. 确定处理脚本的作用、顺序、输入输出、伪代码/规则、异常处理、支持状态、对应实现位置。
7. 已实现、待下游实现、已实测及测试版本；原内容还原与换主题迁移的验收范围、已知偏差。

## 每步完整卡片

每步写：编号/任务；由文字模型、图片模型或脚本执行；模型绑定；输入变量、来源与格式；完整模板与消息角色；槽位含义/来源/是否可改；运行时附加文字；输出结构与数量；下游去向；正常调用次数及重试上限；真实图片输入清单；实现状态与对应证据。

模板和本轮实例同时提供。生图前第3步的所有实际提示词须可查看；第6步至少有每类步骤的完整展开例子，不能把未执行文字步骤的预测输出说成真实输出。

## 源文件与当前生成能力

现有 flowkit.py 的 render 只生成基础spec.md，plan生成运行预览，仍不消费handoff执行模型。新增scripts/render_review.py配合assets/review-shell.html，将Agent派生的阶段view.json渲染为离线HTML；不是flow.json的全自动语义转换器。Agent负责补齐完整spec、派生页面数据并核对真实来源。HTML是审阅说明，不是生成应用。

为避免手工维护多份事实，需要补充的信息统一保存在 flow.json 的可选顶层 `handoff` 对象，作为文档元数据：
- `input_contract`：未来输入、固定/可变项与已确认决定；
- `page_rules`：页型、容量、数量公式、上下限与异常；
- `model_bindings`：配置与实测执行器/型号、未绑定项；
- `step_contracts`：按现有 step.id 对应的补充说明、system提示词、运行时后缀、脚本职责、实现状态；
- `verification`：模板版本/哈希、还原/迁移/完整链路各自状态、证据相对路径、认可范围与偏差。

普通步骤模板仍以 steps[].prompt 或其 prompt_file 为唯一来源，handoff 不复制维护另一套同名模板。系统消息或后缀若写在 handoff 中，必须标明“待执行器实现”，除非确有实际适配器并保存了调用证据；旧 flowkit 不发送它们。文档不得把元数据当已生效参数。

默认顺序：改flow.json → flowkit validate → 按case-operations补齐handoff与实际示例 → casebook deliver同源生成完整HTML、spec、清单和ZIP → 检查。flowkit render仅用于旧版基础规格，会覆盖已有spec补充，不用于最终交付包的重建。casebook不会推断缺失的规律或元数据，字段不完整会明确报出。

HTML 使用本地相对路径引用附件，完整提示词以文本呈现并进行HTML转义；参考素材不得成为可执行脚本。默认使用紧凑列表、侧边抽屉与互斥标签页，提示词代码框可复制、槽位高亮；不平铺全文或用长距离锚点跳转。完整内容仍在文件内，不依赖聊天记录或外网。给下游工具完整文件夹，不仅一张截图。

## 脚本如何搬运

对每项处理注明：现有 flowkit 已支持、Agent 本轮手工完成，或待下游实现。引用 flowkit 能力时给出技能版本和脚本路径；下游无该脚本时，应随交付附带需要的脚本及许可证，或提供完整确定规则供重新实现，不留下不可访问的本机路径作为唯一依赖。新增业务逻辑未实现时只交规格，不声称可直接运行。

## 交付前核对

- 三个主文件的步骤、模板、页数规则和模型说明一致，完整模板能复制，附件链接有效。
- 一次正常运行的调用数与输出数可从输入计算；图片页数不等于内容条数；测试额外调用独立统计。
- 早期还原用的模板与最终版本是否一致；新增文字链路和改过的模板不能继承未经验证的“已测试”标记。
- 用户原图不在纯文字生图调用输入中；若图片辅助流程存在，独立披露并标注未/已测试。
- 不包含密钥；没有虚构提示词、模型实测、脚本实现和用户验收。

## 定稿工具新增的交接字段

slot_contracts：按模板槽位名填写source与description，注明来源、含义和是否可改。step_contracts可用example_prompt_file/example_output_file指向实例，注明是否实际执行；缺实例须example_note解释。script_contract.files列实际脚本相对路径，完整实现会展示在HTML。系统消息/后缀仍遵循前述执行边界。

文件数量不固定。默认每阶段版本2个文件（HTML＋view.json），固定入口2个文件，加case.json、源图、提示词、结果和真实证据。最终包只按明确清单复制需要的附件，自动生成FILES.md和files.json，不能把完整工作区或其他案例装进去。历史test的绝对来源路径可作为溯源文本；运行依赖与展示链接必须在包内。
