# AI 图文素材流程 · 规格定义 v0.4

本文档规定当前 flowkit 可表达的基础流程。完整交付还须遵循 delivery-contract.md，区分已有执行能力与待下游实现的部分；其他工具可据此实现应用，本技能本身不建应用。

v0.4 相对 v0.3 的变化（爆款复刻）：
- 每个玩法以一篇具体的参考笔记为起点，新增 `reference`（原图按顺序、原标题、原正文、原标签）。
- 每个生图步骤新增提示词设计说明 `design`，分四层：风格层、关系层、变化层、不照搬。写法见 `image-prompt-guide.md`。
- 新增 `transfer_input`（迁移测试输入）；`sample_input` 定位为还原测试输入。
- 新增提醒 D13～D17，见 6.1。
- 新增第 15 节“复刻验收”。

v0.3 相对 v0.2 的变化：
- 每个玩法的唯一源文件是 `flow.json`（格式见 `flow-json.md`），人读的《流程规格》`spec.md` 由 `flowkit.py render` 自动生成，包含流程图、每一步的完整提示词、槽位表、连接规则。
- 新增第 14 节“连接规则”：槽位怎么填、图片怎么编号、输出怎么解析、循环怎么收集，全部写死，不留给实现者发挥。
- `{{x}}` 引用列表时改为“全部项按换行拼接”（v0.2 是取第 1 项）。只有 1 行的输入结果不变。新增 `{{x.inline}}`（用“、”拼接）。
- 程序处理新增 `split_lines`，删除 `parse_json`（解析属于文字步骤的输出声明，不单列步骤）。
- 列表数量可以写成表达式，如 `"=16-count(lines)"`。

v0.2 相对 v0.1 的变化：对照现有 7 条产品线做了补全（见第 12 节）；出图上限从 11 提到 14；分组消费一律要求整除；新增文字保真、锚点参考、对齐引用、页面角色、可选图片槽位和质量验收；新增术语表和标准命名。

## 0. 层级、角色与产物

### 0.1 层级

| 层级 | 定义 | 例子 |
|---|---|---|
| 网页 | 一个本地网页，挂载多个玩法，终端用户先选玩法再输入 | 内容工厂网页 |
| 玩法 | 终端用户可以选择的一种产出方式；一个玩法对应一份《流程规格》 | 爆米花团团 IP 漫画、标题生成盘点图鉴 |
| 流程类型 | 结构相同的玩法归为一类，只用于分类，不单独运行 | IP 漫画双宫格、知识卡片 |

本文档只定义单个玩法怎么写。多个玩法如何组成一个网页，放到建站阶段再定（见 T1）。

### 0.2 角色

| 角色 | 做什么 |
|---|---|
| 管理员 | 使用 Skill，通过对话把一个玩法定义清楚，产出《流程规格》 |
| 终端用户 | 在网页里选择玩法、输入文字或图片，拿到成品素材 |
| 建站 Agent | 读取《流程规格》和建站提示词，生成本地网页 |

错误提示分两类：定义阶段的问题提醒管理员，运行阶段的问题提醒终端用户。

## 1. 全局约束

以下是当前 flowkit 的执行约束，不代表所有下游工具的能力或用户必须接受的产品规则。超出其表达能力时，注明待下游实现，不宣称当前脚本可运行。

| 编号 | 约束 | 值 |
|---|---|---|
| G1 | 用户文字的分项方式 | 按换行拆分，一行一项；去掉首尾空格，忽略空行；长段落写在同一行。空行不表示分组，分组只按位置计算（见 5.1） |
| G2 | 用户图片数量 | 0～1 张 |
| G3 | 预置图数量 | 每个玩法 0～3 张 |
| G4 | 单次模型调用的图片总数 | 不超过 5 张，不论来源（用户图、预置图、已生成的图）。文字模型和生图模型都适用 |
| G5 | 单次运行的最终出图数量 | 1～14 张，程序拼接出的图也算在内 |
| G6 | 生图模型 | 外部脚本默认 gpt-image-2，可配置覆盖；内置工具按实际披露，未知写未披露 |
| G7 | 文字模型 | 按步骤需求绑定，只有实际读图步骤才需要图片理解 |
| G8 | 模型输出不合规时 | 自动重试，最多 2 次；仍失败则报错并停止 |
| G9 | 用户输入不合规时 | 不自动截断或修正，提示终端用户修改后重新提交 |
| G10 | 分组消费的整除 | 列表数量必须能被组大小整除，没有例外，不存在"尾组" |
| G11 | 输入至少一项 | 每个玩法至少要有 1 个必填输入，可以是文字，也可以是图片 |

## 2. 数据（变量）

流程中的所有数据都是变量。每个变量有一个英文 ID，写代码和槽位时用；还有一个中文显示名，在网页上展示。ID 只能用小写字母、数字和下划线。

| 类别 | 来源 | 类型 | ID 规则 | 例子 |
|---|---|---|---|---|
| 用户文字 | 终端用户填写 | 列表（每行一项） | 自定义 | `title`、`lines` |
| 用户图片 | 终端用户上传 | 图片 | 固定为 `user_image` | 用户原图 |
| 预置图 | 玩法自带，每次相同 | 图片 | 固定为 `preset_1`～`preset_3` | IP 角色参考图 |
| 步骤输出 | 前面步骤的结果 | 文本 / 列表 / JSON / JSON 列表 / 图片 / 图片列表 | 在步骤里声明 | `subtitles`、`cover` |

用户文字一律按列表处理。只允许填一行的输入，就是行数范围为 1～1 的列表。

### 2.1 用户文字输入的字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` / `name` | 是 | 如 `lines` / 漫画台词 |
| `rows` | 是 | 行数范围，如 `1..16`；固定行数写成 `16..16` |
| `multiple_of` | 否 | 行数必须是几的倍数，被 `grouped(k)` 消费时必填，值为 k |
| `required` | 是 | 是否必填 |
| `max_chars` | 否 | 单行字数上限 |
| `verbatim` | 否 | `true` 表示原文必须逐字出现在最终图片里，见 5.6 |
| `placeholder` | 是 | 输入框里的示例文字 |

### 2.2 用户图片的字段

`enabled`（是否启用）、`required`（是否必填）、`name`（显示名）、`hint`（上传说明）。

### 2.3 预置图的字段

`id`、`file`（文件名）、`purpose`（用途说明），并随规格一起提供图片文件。预置图属于玩法，同一个流程类型下的不同 IP 各自有自己的预置图。

## 3. 槽位

槽位是提示词里的占位符，执行时替换成变量的值。

### 3.1 文字槽位

| 写法 | 含义 |
|---|---|
| `{{x}}` | 文本原样填入；列表按换行拼接全部项；JSON 对象填入 JSON 文本；空值填空字符串 |
| `{{x[i]}}` | 列表的第 i 项，i 从 1 开始 |
| `{{x.all}}` | 整个列表按换行拼接（与 `{{x}}` 相同，写出来更清楚） |
| `{{x.inline}}` | 整个列表用“、”拼接成一行 |
| `{{x.count}}` | 列表的项数 |
| `{{x.字段}}` | JSON 的某个字段，可以多级，如 `{{plan.cover.title}}` |
| `{{x.current}}` | 循环中，列表 x 与当前轮序号相同的那一项（对齐引用，见 5.5） |
| `{{x.current.字段}}` | 对齐引用 JSON 列表时，取当前项的字段 |

### 3.2 图片槽位

| 写法 | 含义 |
|---|---|
| `{{img:x}}` | 必选图片。执行时把这张图一并传给模型 |
| `{{img?:x}}` | 可选图片。x 有值就传，x 为空就整个去掉，连同它所在的那一行提示词一起删除 |
| `{{img:x[i]}}` | 图片列表的第 i 张 |

图片槽位可以用在文字提示词里，让模型识别图片内容；也可以用在生图提示词里，作为参考图。图片按槽位在提示词中出现的先后顺序传给模型，顺序由写提示词的人决定，系统不重新排序。

### 3.3 循环上下文槽位

| 写法 | 含义 |
|---|---|
| `{{item}}` / `{{item.字段}}` | `per_item` 模式下的当前项；当前项是 JSON 时可以取字段 |
| `{{group[j]}}` | `grouped(k)` 模式下当前组的第 j 项，j 从 1 到 k |
| `{{index}}` | 当前轮序号，两位数，从 01 开始 |
| `{{total}}` | 本次循环的总轮数 |
| `{{img:prev}}` | 上一轮生成的图片，仅在 `ref_mode = chain` 时可用 |
| `{{img:anchor}}` | 锚点图片，仅在 `ref_mode = anchor(n)` 时可用 |

## 4. 步骤

### 4.1 步骤类型

| 类型 ID | 名称 | 做什么 | 输出 |
|---|---|---|---|
| `text` | 文字模型调用 | 把填好的提示词发给文字模型；带图片槽位时，模型同时识别图片 | 文本 / 列表 / JSON / JSON 列表 |
| `image` | 生图模型调用 | 把填好的提示词发给实际选定的生图执行器；外部型号来自配置，内置型号按工具披露。没有图片槽位时是文生图，有图片槽位时是图生图 | 图片 |
| `code` | 程序处理 | 不调用 AI、结果确定的操作 | 任意 |

### 4.2 `code` 步骤的标准操作

| 操作 ID | 作用 | 参数 |
|---|---|---|
| `merge` | 把多个列表按顺序合并成一个；为空的列表跳过 | `lists` |
| `split_lines` | 把一段文本按 G1 拆成列表 | 文本变量 |
| `pick` | 从 JSON 里取出某个字段，作为新变量 | `path`，如 `plan.pages` |
| `slice` | 取列表的一段 | `list`、`start`、`end`（从 1 开始，含两端） |
| `compose` | 把多张图按指定版式拼成一张 | `images`（按顺序）、`layout`（`row` / `column` / `grid:行x列`）、`gap`、`background`、`size` |
| `overlay_text` | 把文字画到图片上 | `image`、`text`（可含文字槽位）、`position`（top / center / bottom）、`font`、`font_size`、`color` |

需要表中没有的操作时，在规格里写清输入、输出和算法，保证建站 Agent 能照着实现。

### 4.3 步骤字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 步骤 ID，命名规则见第 11 节 |
| `name` | 是 | 中文名，如"生成小标题" |
| `type` | 是 | `text` / `image` / `code` |
| `role` | image 步骤和 compose 操作必填 | 页面角色，见 5.7 |
| `reads` | 是 | 读取的变量 ID 列表 |
| `prompt` | text / image 必填 | 提示词全文，含槽位 |
| `op` | code 必填 | 操作 ID 及参数 |
| `consume` | 是 | `once` / `per_item` / `grouped(k)` / `whole_list`，见 5.1 |
| `over` | consume 不为 `once` 时必填 | 被消费的列表变量 ID |
| `when` | 否 | 执行条件，见 5.2 |
| `ref_mode` | 循环中引用已生成图片时必填 | `fixed` / `anchor(n)` / `chain`，见 5.4 |
| `output` | 是 | 输出变量 ID、类型、格式要求。列表写数量，JSON 写字段 |
| `retry` | 否 | 默认遵循 G8 |
| `confirm` | 否 | `true` 表示该步完成后暂停等人工确认，见 5.3 |
| `image_size` | image 必填 | 尺寸，写成 `宽x高`。只能用 `1024x1024`（1:1）、`1024x1536`（2:3 竖）、`1536x1024`（3:2 横）；这个值原样发给接口，写别的会被拒绝 |
| `checks` | 否 | 本步输出的验收项，见第 7 节 |

## 5. 控制方式

### 5.1 消费方式 `consume`

`consume` 规定一个步骤怎么读取列表。它挂在步骤上，不挂在输入上，因为同一个列表可能被不同步骤用不同方式读取。

| 值 | 含义 | 调用次数（列表 N 项） | 典型场景 |
|---|---|---|---|
| `once` | 不循环，执行 1 次 | 1 | 生成发布文案 |
| `per_item` | 每一项单独执行一次 | N | 单个表情包、故事 IP、知识卡内页 |
| `grouped(k)` | 按位置每 k 项一组（第 1～k 项为第 1 组，依此类推），每组执行一次 | N / k | IP 漫画 k=2、三宫格知识卡 k=3 |
| `whole_list` | 整个列表一次性交给模型，用 `{{x[1]}}`～`{{x[N]}}` 或 `{{x.all}}` 引用 | 1 | 16 宫格表情包 |

`per_item` 和 `grouped(k)` 每一轮的输出，按轮次顺序收集成一个列表，作为该步骤的输出变量。例如每轮生成一张图，输出就是图片列表；每轮输出一个 JSON，输出就是 JSON 列表。

`grouped(k)` 的分组只看位置。用户在组与组之间有没有写空行都不影响结果，空行会按 G1 忽略。网页应在输入框旁边实时显示分组预览，比如"第 1 张：A / B"，让用户看到自己的分法。

### 5.2 执行条件 `when`

满足条件才执行，不满足就跳过，跳过时该步输出为空。

| 写法 | 含义 |
|---|---|
| `has(x)` | 变量 x 非空。x 可以是用户图片、步骤输出或 JSON 字段，如 `has(plan.summary)` |
| `not has(x)` | 变量 x 为空 |
| `count(x) < 16` | 列表项数比较，运算符有 `<` `<=` `=` `>=` `>` |
| `A and B` / `A or B` | 组合条件 |

分支写法：两个步骤的条件互斥时，可以声明同一个输出 ID，后续步骤直接引用这个 ID，不用关心走的是哪条分支。条件不互斥的步骤不能共用输出 ID。

如果只是"有图就带上、没图就不带"，而提示词本身不变，优先用可选图片槽位 `{{img?:x}}`，不必拆成两个分支。

### 5.3 人工确认 `confirm`

设为 `true` 的步骤完成后，流程暂停并展示这一步的输出。终端用户可以直接修改文字结果、重新生成这一步，或者确认后继续。修改后的结果必须重新通过该步的输出校验。建议把确认点放在生图前的最后一个文字步骤，因为这时改文字最便宜，出图成本最高的环节还没开始。

### 5.4 参考已生成的图片

后一步用前一步生成的图，有两种情况。

情况一是跨步骤引用，比如内页参考封面、壁纸参考头像。直接在提示词里写 `{{img:cover}}`，并把 `cover` 加进 `reads`。执行顺序由依赖关系自动决定，不需要额外声明。

情况二是在同一个循环里引用本循环生成的图，这时要声明 `ref_mode`：

| 值 | 含义 | 执行方式 | 典型场景 |
|---|---|---|---|
| `fixed` | 每一轮都参考同一张在循环之前就已生成的图 | 并行 | 所有内页参考封面 |
| `anchor(n)` | 先单独执行第 n 轮；它完成后，其余各轮都用 `{{img:anchor}}` 参考第 n 轮的结果。第 n 轮自己的提示词里会去掉这个槽位 | 第 n 轮先执行，其余轮并行 | 手帐百科以第 1 页为锚点，国风知识卡以第 2 页为锚点 |
| `chain` | 每一轮用 `{{img:prev}}` 参考上一轮的结果；第 1 轮去掉这个槽位 | 逐张串行 | 连续剧情、逐页演变 |

已生成的图也计入 G4 的 5 张上限。

### 5.5 对齐引用 `{{x.current}}`

一个步骤循环列表 A 时，可以用 `{{B.current}}` 取列表 B 中与当前轮序号相同的那一项。前提是 A 和 B 长度相同，这个要求在定义阶段声明，在运行阶段校验。

典型场景是故事 IP：先对每行文字生成一条画面规划（`scenes`），再循环页面文字出图，每一轮用 `{{scenes.current.helper_scene}}` 取对应的画面规划。

### 5.6 文字保真 `verbatim`

用户文字输入或步骤输出标记为 `verbatim = true` 后，有三个效果：

- 用到它的文字步骤只能读取它，不能输出替代它的版本；生图提示词必须直接引用原变量。
- 生图提示词里必须包含"以下文字逐字呈现，不改写、不漏字、不多字"这一类指令。
- 自动加上一条视觉验收：文字准确，见第 7 节。

适用场景包括漫画对白、表情包文字、故事页面文字。模型补全出来的行也可以在输出上标记 `verbatim`，这样补全行进图时同样不能被改写。

### 5.7 页面角色 `role`

每个 `image` 步骤和 `compose` 步骤都要声明它产出的页面角色。角色决定三件事：输出的排序、下载文件名、网页上的显示名。

| 角色 ID | 显示名 | 说明 |
|---|---|---|
| `cover` | 封面 | 一组图的第一张 |
| `overview` | 总览页 | 概括全部内容的一页 |
| `detail` | 详情页 | 逐条或逐组展开的内页 |
| `summary` | 汇总页 | 收尾页，通常可选 |
| `panel` | 单格图 | 故事 IP、单张 IP 图 |
| `comic` | 多格漫画 | 双格、三格等，一张图里有多格 |
| `sticker` | 表情包 | 单张表情包 |
| `grid` | 合集图 | 16 宫格等，多个内容单元在一张图里 |
| `avatar` / `wallpaper` / `compare` | 头像 / 壁纸 / 对比图 | 头像三件套 |
| `asset` | 资产图 | 封面、三视图等可复用素材 |

需要上表以外的角色时，可以自定义，并写明显示名。

## 6. 校验

### 6.1 定义阶段（Skill 检查，提醒管理员）

| 编号 | 检查项 |
|---|---|
| D1 | 出图数量：按所有输入取最小值和最大值分别推算，最终出图总数在 1～14 之间（G5）。程序拼接出的图也计入 |
| D2 | 每一次模型调用的图片槽位数不超过 5（G4），可选槽位按"有值"计算 |
| D3 | 每个槽位引用的变量都已定义，并且在当前步骤之前产生 |
| D4 | 必选图片槽位 `{{img:x}}` 引用可能为空的变量时，所在步骤带有对应的 `when` 条件；否则改用 `{{img?:x}}` |
| D5 | 预置图不超过 3 张，且文件已提供 |
| D6 | 每个 text 步骤都声明了输出格式，列表写明数量，JSON 写明字段 |
| D7 | 每个 image 步骤都声明了 `image_size` 和 `role` |
| D8 | 整除：每个 `grouped(k)` 的被消费列表，数量范围里只有 k 的倍数，见下表 |
| D9 | 对齐引用 `{{B.current}}` 的两个列表，已声明长度相同 |
| D10 | `verbatim` 的变量没有被文字步骤改写后再进图 |
| D11 | 至少有 1 个必填输入（G11） |
| D12 | `anchor(n)` 的 n 不大于被循环列表的最小长度 |
| D13 | （提醒）有参考案例：原图文件存在，标题、正文、标签齐全 |
| D14 | （提醒）每个 image 步骤写了 `design` 的风格层、关系层、变化层 |
| D15 | （提醒）每个 image 步骤的提示词至少有一个随输入变化的槽位（预置图不算），否则每次会画出差不多的图 |
| D16 | （提醒）有迁移测试输入 `transfer_input` |
| D17 | （提醒）有固定主角（`subject.fixed`）但生图提示词缺"保持【图N】的……"说明 |

D8 的处理方式：

| 被消费的列表来源 | 处理 |
|---|---|
| 用户输入 | 在输入上声明 `multiple_of = k`，行数范围的上下限都要是 k 的倍数，如 `2..28`；或者加一个 text 补全步骤，补到 k 的倍数 |
| 模型输出 | 提示词和输出校验都写明"数量必须是 k 的倍数"，不合规时按 G8 重试 |

除不尽不允许用"尾组单独出图"来兜底。发现除不尽时，Skill 必须提醒管理员，从上面两种方式里选一种改掉。

### 6.2 运行阶段（网页检查，提醒终端用户）

| 编号 | 检查项 | 处理 |
|---|---|---|
| R1 | 行数超出范围、必填项为空、单行超出字数 | 提交前拦截，指出是哪一项、第几行 |
| R2 | 行数不是 `multiple_of` 的倍数 | 提交前拦截，提示"需要 k 的倍数，当前 n 行" |
| R3 | 图片超过 1 张，或格式不支持 | 提交前拦截 |
| R4 | 模型输出的数量或格式不合规 | 自动重试，最多 2 次；仍失败则停止并显示原始输出（G8） |
| R5 | 模型接口报错 | 停在该步，显示错误，允许单步重试 |
| R6 | 对齐引用的两个列表长度不一致 | 视为上一个 text 步骤输出不合规，按 R4 处理 |

## 7. 质量验收 `checks`

验收分两类。

| 类别 | 由谁执行 | 验收项 |
|---|---|---|
| 自动验收 | 程序 | JSON 格式、字段齐全、列表数量、图片张数、画布比例、文件是否生成 |
| 复刻验收 | 人工对照原作 | 见第 15 节 |
| 视觉验收 | 文字模型看图，或人工 | 文字准确（`verbatim` 的文字逐字出现）、角色一致（与预置图的识别点、主色、轮廓、标志物一致）、有图片输入时检查参考图是否按约定使用；纯文字验证检查零图片输入；格数正确（如 4×4 共 16 格） |

视觉验收由Agent依据实际输出检查并记录，用户再确认整体效果。flowkit不执行自动视觉验收；`auto_review = true`不能让现有执行器自动增加模型调用。若用户需要自动检查/修复，将其写成待下游实现的明确步骤，补齐模型、提示词、调用数和重试规则；未经实测不能标成已支持。

## 8. 输出

每个玩法都要声明最终交付的内容：

| 字段 | 说明 |
|---|---|
| 展示顺序 | 按页面角色排序：`cover` → `overview` → `detail` / `panel` / `comic` / `sticker` → `summary` → `compare`；文字按 标题、正文、标签 排序 |
| 显示名 | 默认使用角色显示名，可以覆盖 |
| 可复制 | 文字项提供一键复制，标签复制时带 `#` |
| 下载 | 单张下载和打包下载都支持；文件名为 `序号_显示名.png`，如 `00_封面.png`、`01_详情页.png` |
| 数量 | 分开写两个数：内容单元数（如 16 格）和出图数（如 1 张） |

outputs声明日常生成要交给终端用户的产物；当前技能的流程交付另需保留实际提示词、中间文字、原始输出与测试记录，按delivery-contract打包必要证据。不能因outputs没列它们而丢掉执行依据。

## 9. 《流程规格》的交付形式

每个玩法交付一个文件夹：

```
<玩法 ID>/
  flow.json        唯一源文件，机器可读（格式见 flow-json.md）
  reference/       参考笔记原图，按顺序 01.png、02.png……
  spec.md          由 `flowkit.py render` 生成的《流程规格》，人读
  presets/         预置图文件（0～3 张）
  prompts/         （可选）较长的提示词可以放成单独的 .txt，用 prompt_file 引用
```

`spec.md` 固定包含 9 节：1 概述（出图数、调用次数、参考案例）、2 流程图（Mermaid）、3 输入、4 预置图、5 步骤详情（生图步骤的提示词设计说明、每步的完整提示词、槽位表、每次调用图片数、输出与连接规则、质量验收）、6 变量连接总表（每个变量由谁产生、被谁使用）、7 输出交付、8 通用连接规则（第 14 节原文）、9 校验结果（D1～D17）。

`spec.md` 不要手改。要改就改 `flow.json`，再重新生成。

## 10. 现有产品线的规格示例

以下每一例对应对照文档里的一条产品线，用来证明本定义能完整表达它们。提示词只写出槽位的位置，全文由各玩法补充。

完整可运行的 `flow.json` 见 Skill 的 `examples/` 目录（knowledge_card、ip_comic、meme、meme_grid、story_ip、avatar_pack 各一例），下面是结构摘要。

### 10.1 知识卡片：标题生成盘点图鉴（流程类型 `knowledge_card`）

- 输入：`title` / 标题 / `1..1`
- 预置图：无

知识卡片只有两种页面：第 1 张是封面，后面都是正文页。

| # | id / name | type | consume | 关键设置 | output |
|---|---|---|---|---|---|
| 1 | `txt_points` 生成正文要点 | text | once | prompt 含 `{{title}}`；confirm = true | `points` 列表，数量由玩法定（如 6～10 项） |
| 2 | `img_cover` 生成封面 | image | once | role = cover；prompt 含 `{{title}}` | `cover` |
| 3 | `img_pages` 生成正文页 | image | per_item，over `points` | role = detail；prompt 含 `{{title}}` `{{index}}` `{{item}}` `{{img:cover}}` | `pages` |
| 4 | `txt_copy` 生成发布文案 | text | once | prompt 含 `{{title}}` `{{points.all}}` | `copy` JSON：`title`、`body`、`tags` |

- 出图：1 + 正文页数，最多 14 张 ✓
- 同类型的其他玩法只改局部：

| 玩法 | 与上表的区别 |
|---|---|
| 手填版 | 去掉步骤 1，用户直接输入 `title` 和多行 `points` |
| 以第 n 张为锚点 | 步骤 3 去掉 `{{img:cover}}`，设 `ref_mode = anchor(n)` |
| 三宫格正文页 | 步骤 3 改为 `grouped(3)`，`points` 数量必须是 3 的倍数 |
| 情绪故事配图 | 用户输入 `lines`，`multiple_of = 2`，步骤 3 改为 `grouped(2)` 出 1×2 图 |

### 10.2 IP 漫画双宫格：爆米花团团 IP 漫画（流程类型 `ip_comic`）

- 输入：`lines` / 漫画台词 / `2..22` / `multiple_of = 2` / `verbatim = true`
- 预置图：`preset_1` = IP 角色参考图

| # | id / name | type | consume | 关键设置 | output |
|---|---|---|---|---|---|
| 1 | `img_comics` 生成双格漫画 | image | grouped(2)，over `lines` | role = comic；3:4；prompt 含 `{{img:preset_1}}` `{{group[1]}}` `{{group[2]}}` | `comics` |
| 2 | `txt_copy` 生成发布文案 | text | once | prompt 含 `{{lines.all}}` | `copy` JSON：`title`、`body`、`tags` |

- 出图：1～11 张 ✓（上限可以放宽到 28 行、14 张，目前保持和现有产品一致）
- 用户可以每两行空一行，也可以连续写，分组只按位置，结果相同
- 白虎、粉发辣妹、奶油棕胖兔等 IP 都是同一份结构，只换 `preset_1` 和提示词里的角色描述

### 10.3 单个表情包（流程类型 `meme`）

- 输入：`lines` / 表情包文案 / `1..11` / `verbatim = true`
- 预置图：`preset_1` = IP 角色参考图（可选；有的玩法没有）

| # | id / name | type | consume | 关键设置 | output |
|---|---|---|---|---|---|
| 1 | `img_memes` 生成表情包 | image | per_item，over `lines` | role = sticker；1:1；prompt 含 `{{item}}`，有 IP 时含 `{{img:preset_1}}` | `memes` |

- 出图：1～11 张 ✓
- 需要发布文案时，追加一个 `txt_copy` 步骤，写法和 10.2 相同
- 旧配置里"一段整文案生成单图"的变体，另写成一个玩法：`lines` 设为 `1..1`，consume 改为 `once`，出 1 张

### 10.4 16 宫格表情包：爆米花团团 16 宫格（流程类型 `meme_grid`）

- 输入：`lines` / 贴纸文案 / `1..16` / `verbatim = true`
- 预置图：`preset_1` = IP 角色参考图

| # | id / name | type | consume | 关键设置 | output |
|---|---|---|---|---|---|
| 1 | `txt_fill_lines` 补全贴纸文案 | text | once | when `count(lines) < 16`；prompt 含 `{{lines.all}}` `{{lines.count}}`，要求补足 16 − n 行且不改动原行 | `extra_lines` 列表，数量 = 16 − count(lines)，`verbatim = true` |
| 2 | `op_merge_lines` 合并文案 | code | once | op = merge(`lines`, `extra_lines`) | `all_lines` 列表，16 项 |
| 3 | `img_grid` 生成 16 宫格 | image | whole_list，over `all_lines` | role = grid；1:1；prompt 含 `{{img:preset_1}}` `{{all_lines[1]}}`～`{{all_lines[16]}}`；checks 含"16 格齐全、文字准确、角色一致" | `grid` |

- 内容单元 16 个，出图 1 张 ✓
- 不足 16 项时的处理方式，每个玩法只能选一种：选"模型补全"就用上表；选"用户补齐"就把 `lines` 设为 `16..16`，并删掉步骤 1、2

### 10.5 故事 IP：小和尚故事 IP（流程类型 `story_ip`）

- 输入：`lines` / 故事逐行文案 / `1..14` / `verbatim = true`

|---|---|---|---|---|---|
| 1 | `txt_scenes` 规划辅助画面 | text | per_item，over `lines` | prompt 含 `{{item}}`；只规划画面，不改写文字 | `scenes` JSON 列表，长度 = count(lines)；每项含 `helper_scene`、`purpose`、`key_objects`、`avoid` |

- 步骤 1 是逐行调用；如果要省调用次数，也可以改成 once，一次输出整个列表。两种写法在规格里都成立，结果相同

### 10.6 头像三件套：水彩马克笔手绘头像（流程类型 `avatar_pack`）

## 14. 连接规则

提示词只说明“发给模型什么”；连接规则说明“前一步的结果怎么变成后一步提示词里的内容”。以下规则对所有玩法相同，`spec.md` 第 8 节会原样附上，建站 Agent 和 flowkit 都按此执行。

**R-1 用户文字拆分**：按换行拆成列表，去掉每行首尾空格，忽略空行。空行不表示分组。

**R-2 文字槽位填入**：见 3.1 和 3.3。列表默认按换行拼接；JSON 对象填入 JSON 文本；空值填空字符串。

**R-3 图片槽位填入**
- 每次调用中，图片按槽位在提示词里出现的先后编号为 图1、图2……，槽位位置替换为文字 `【图N】`，图片按同样顺序传给模型。
- `{{img?:x}}` 为空时，删除槽位所在的整行；`anchor(n)` 的第 n 轮、`chain` 的第 1 轮，删除含 `{{img:anchor}}` / `{{img:prev}}` 的整行。
- 写提示词时，把图片槽位单独放一行，后面用“【图1】是……”说明它的作用。这样删除整行时不会破坏句子。

**R-4 模型调用**（OpenAI 兼容接口）
- 文字：`POST {Base URL}/chat/completions`，一条 user 消息，content 按提示词顺序由文字段和图片段（data URL）交替组成。
- 生图：无图片时 `POST /images/generations`（JSON：model、prompt、size、n=1）；有图片时 `POST /images/edits`（multipart：model、prompt、size、n=1、按顺序的多个 `image[]`）。返回 `data[0].b64_json` 或 `data[0].url`。

**R-5 输出解析**
- text：去掉代码围栏和首尾空白。
- list：是 JSON 字符串数组就直接用；否则按行拆分、去空行、去掉行首编号（`1.` `01、` `-` `第3条：` 等）。
- json：取第一个 `{` 到最后一个 `}`；json_list：取第一个 `[` 到最后一个 `]`。
- 检查 `count`、`fields`、`multiple_of`，不通过视为不合规。

**R-6 失败处理**：模型输出不合规自动重试最多 2 次；接口报错停在该步，可单步重试；用户输入不合规在提交前拦截。

**R-7 循环与顺序**：步骤按编号执行；`when` 不满足则跳过、输出为空；每轮结果按轮次顺序收集成列表；无参考或 `fixed` 可并行，`anchor(n)` 先跑第 n 轮，`chain` 串行。

**R-8 人工确认**：暂停后用户可改文字、重跑本步或继续；改过的结果重新走 R-5 检查，条数不能变。

**R-9 交付**：按输出表顺序；图片文件名 `序号_显示名.png`，图片列表再加两位序号；标签复制时带 `#`。

## 15. 复刻验收

第3步默认先用抽出的模板回填原内容做还原对照；用户可明确跳过。第7步迁移按需执行，未迁移也可交付方案，但须标明验证范围。两类测试含义如下：

| 测试 | 输入 | 通过标准 |
|---|---|---|
| 还原测试 | `sample_input`，尽量用原作自己的内容 | 结果和原作的风格、版式、图文关系接近 |
| 迁移测试 | `transfer_input`，主题完全不同的内容 | 风格和版式保持不变；画面内容跟着新输入变化，不出现原作的具体物件 |

只通过一项时，另一项仍未验证或尚未通过，需根据实际失败定位原因。纯文字与图片辅助证据、冻结模板及执行器记录见 execution-validation.md；不能据单项结果直接断言原因。

生图提示词按四层组织（详见 `image-prompt-guide.md`）：

| 层 | `design` 字段 | 每次运行 |
|---|---|---|
| 风格层 | `style` | 固定 |
| 关系层：文字和画面的关系、画面怎么从文字推出 | `relation` | 固定 |
| 变化层：来自槽位的内容 | `varies` | 变 |
| 不照搬：原作中只属于某张图的具体物件 | `avoid` | 固定 |

本技能交付的 flow.html 应展示参考案例与完整流程；下游是否做应用由后续技能处理。
