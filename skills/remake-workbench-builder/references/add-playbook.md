# 给已有工作台添加玩法

用户可以说：“使用第二个技能，把这个拆解交付包添加到我的工作台；保留已有玩法、设置和历史。我希望日常只输入主题。”用户只需要提供交付包位置与目标工作台，不需要手改程序。

## 先识别，再接入

1. 找到目标工作台、项目规则、catalog.json、产品目录和当前运行地址。新增时以这个工作台当前代码与已确认界面为准，不用 assets/base 覆盖已有应用。
2. 找到用户确认的模板与版本。读取完整 flow、提示词、素材、脚本和验收记录；历史对话只是定位证据。不得把另一个名字相似的模板直接接上。
3. 核对“原模板要求用户填什么”和“用户希望日常填什么”。若原模板需要完整文案，用户希望只输入主题，须明确这是新增文字规划步骤，不是简单导入。经用户确认后，在新交付目录保存新 flow，原模板保持不变。
4. 将人物、画风、版式、署名、尾页规则分别区分为固定配置与每日输入。不沿用参考作者署名；未知用户署名先留空并说明。不让用户每天重新填写固定人物描述。不默认把所有模板都变成知识卡的6—14页流程。
5. 写明每一步输入输出、数量、顺序、完整提示词、变量展开、实际图片输入数量、比例及确认点。新增主题规划必须有结构校验；不合规停止或有限重试，不静默截断。

## 执行与登记

- 同契约玩法：使用目标工作台 manage.py 登记新版本。
- 新契约玩法：先实现独立适配器，再登记。不得绕过 check_flow 校验。共同执行层须按玩法选择带图或纯文字端点；页面数量、提示词数量、输入提示、详情流程和确认说明也必须随玩法变化。
- 接口设置按 model-setup.md 主动询问；已有服务复用。图片尺寸与参考图能力单独核对。缺少接口时继续模拟验证，不用 Agent 内置生图证明网页API兼容。
- 登记时保留已有 catalog 其他条目、连接设置、旧产品版本与历史。相同源重复登记幂等；新版本不能影响旧任务所使用的提示词。
- 导入原有样张时只放玩法库，标明原模式及验收范围。旧版“完整文案输入”的样张不能标成新版“主题扩写”的验证结果。

## 验证与交付

必须验证：原玩法仍能用、新玩法只出现约定输入、分页数量/顺序正确、提示词展开不串页、图片输入数量正确、确认前零生图调用、失败只补未完成页、重画保留旧版、历史与示例分开、导出无密钥。检查网页的玩法卡、详情和选择入口。

交付说明分清：已接入、模拟测试通过、真实模型是否试跑、用户是否认可新结果。给用户可打开的工作台，不以写了方案代替执行。视觉调整先在实际工作台确认，再另行更新 DESIGN 与共同底座。

## 本次实例：青绿动作图解

原流程：7项输入，纯文字生图，封面1＋每2项正文一张共4＋尾页1；无发布文案步骤。
新增主题版：只输入topic → 1次文字调用输出8项正文、封面文案、尾页相关标题和发布稿 → 校验 → 用户确认 → 6次纯文字生图，1024×1536。人物沿用原默认文字设定，署名为空，尾页为通用收尾。三个生图提示词原文保留，只替换变量值。

这是经适配的第二种流程，不是任意 flow 都能直接运行的证明。assets/base已包含两种适配器和四板块界面。新增其他结构仍需实现适配器，禁止静默套用。

新增前按 playbook-presentation.md 准备workbench.json；相同契约可直接使用add_playbook.py，未知契约先在目标工作台完成适配和测试。已有工作台始终保留自己的实现，不整目录覆盖。例子在examples/，其中测试角色图是占位图，不能用来真实生产。
