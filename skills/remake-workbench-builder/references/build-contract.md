# 搭建契约

## 产品决定

一个工作台支持多个玩法。Agent 负责首次搭建、增加产品线和维护提示词；用户日常使用独立网页，不需要打开 Agent。提示词在玩法建立时打磨。任务仅填入该玩法规定的内容、确认流程、生成和交付。单页重画沿用同一输入、提示词和角色；旧图片保留。反复出现的问题应上升到玩法规则维护，不给用户加临时提示词补丁。

第一版：玩法选择、动态输入、内容方案确认、生成状态、失败恢复、单页重画、历史、单张/整套下载、发布文案复制、文字/生图连接。暂不做批量主题、拖拽排版、账号、积分、支付、分销或社群。

## 承接表必须逐项写

- 输入：文本结构/数量/边界、图片用途、预置素材、是否逐字保留。
- 执行：全部 text/image/code 步骤；循环、条件、列表对齐、图片锚定；脚本算法/文件；不支持项明确。
- 提示词：唯一源、槽位展开、系统消息、后缀、图片编号和传参顺序；不得悄悄缩写优化。
- 确认：在哪一步暂停、显示什么、如何继续；用户修改内容时是否允许、需要哪些校验。当前用户明确不做单任务提示词修改；内容编辑并非默认功能。
- 模型：会话工具与程序 API 分开；图像输入、模型名、尺寸均按实际服务能力绑定。占位模型/尺寸不能当成验证过的配置。
- 交付：图片与发布文案分别处理；所有中间数据、实际提示词、模型绑定、版本与旧图保存；密钥不进入任务与导出。
- 证据：原内容还原、变更模板后迁移、外部API验证分别记载；历史案例不冒充新运行。

## 底座与适配器

`assets/base/engine.py` 提供本地持久化、任务状态和兼容接口连接；`card_validation.py` 来源于已审阅的知识卡交付脚本。`manage.py` 将 flow.json 和素材原样复制到不可覆盖的版本目录，登记到 catalog.json。

当前支持两类实例：知识卡为主题 → 6—14页结构数据 → 发布文案 → 确认 → 固定角色逐页生图；青绿图解为主题 → 一次生成整套文案 → 确认 → 6次纯文字生图。两者仅输入一行主题，但分别使用独立校验；页数、确认说明和角色传参不可互相套用。不能因为其他 flow 同名步骤就保证通用兼容。搭建 Agent 要先对比字段、脚本与完整提示词。新增条件、代码、锚点或其他输入须实现新的适配器，再注册；不要放宽检查让未知字段静默通过。

程序不执行交付包中的任意 Python。Agent 审阅后将所需算法纳入受测试的应用代码。新版本发布前对比源提示词与实际请求；运行中使用已登记的不可变玩法版本。升级执行代码时若旧版本语义变化，需要兼容适配器或明确迁移，不把旧任务改成新行为。

## 必经的模型连接询问

承接流程后、完成交付前，必须按 [模型连接引导](model-setup.md) 主动向用户索取所需服务的 Base URL、模型名称和 API Key，并协助配置。已有值沿用，只询问缺项。不得把“有一个设置页面”当作已经完成引导，也不得默默跳过询问后直接报告“缺少连接”。

## 启动与交付

源码方案需要 Python 3.10+；Windows/Mac 启动器减少操作，不等于已经制作包含运行环境的安装包。先由 Agent 检查运行环境并启动。最终给用户可打开的本机地址与再次启动方法。API 配置不齐时仍可查看历史案例和使用历史导出，但不能伪造新生成结果。

首次搭建：`python3 scripts/create_workbench.py --target <新目录> --delivery <交付目录>`。
可选 `--accepted-example`：仅当交付含已审阅的 spending-v1 历史案例时复制7张历史图片，标明来源。
兼容玩法新增/升级：`python3 <工作台>/manage.py <交付目录> --app <工作台>`。该命令不是任意流程转换器。

页面固定为生成工作台、玩法库、生成历史、设置；玩法说明由workbench.json驱动，完整契约见playbook-presentation.md。底座同步不包含开发者data、模型设置、历史任务、产品目录或个人案例；安装样例与真实交付必须区分。
